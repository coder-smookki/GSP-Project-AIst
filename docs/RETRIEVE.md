# retrieve и поиск: как устроен поиск по базе знаний

Документ описывает узел `retrieve` в графе ассистента и весь поисковый слой
поверх него. Код намеренно очищен от пояснительных комментариев: вся логика,
причины и замеры собраны здесь же, с указанием модулей и строк, чтобы исходник
оставался компактным, а объяснения были в одном месте.

## 1. Общий поток

```
вопрос пользователя
        │
        ▼
retrieve (узел графа, agent/graph.py:186)
        │  search.query(query, sections, areas)
        ▼
Search (протокол, search.py:61)
        ├── MockSearch   — заглушка для отладки/тестов
        └── QdrantSearch — боевой путь: dense + BM25 + слияние RRF
        │
        ▼
list[(Chunk, score)] → to_citation() (search.py:46) → Citation (словарь)
        │
        ▼
assistant: [система][история][выдержки с маркерами [n]][память] → ответ
```

Ключевое решение архитектуры: **граф не знает, что под протоколом `Search`** —
заглушка или Qdrant. Фабрика (`factory.py:13`) подставляет реализацию по
настройкам, и смена боевого поиска на заглушку не трогает ни граф, ни
интерфейс.

Поведение фабрики (factory.py:13, 59):

- клиент Qdrant создаётся один раз на процесс и закрывается через `shutdown()`
  — открывать соединение на каждый запрос дорого, копить незакрытые — плохо;
- выбранный `RETRIEVAL_PROVIDER=mock` логируется **предупреждением на каждом
  старте** — «демо на заглушке» не должно быть тихим состоянием;
- при сбое доступа к Qdrant фабрика НЕ подменяет боевой поиск заглушкой:
  синтетический корпус из четырёх чанков выглядел бы как работающая система и
  обманул бы и нас, и жюри. Ошибка честно всплывёт на первом запросе как
  `SearchUnavailable`.

## 2. Узел retrieve (agent/graph.py:186)

Шаги узла:

1. Берёт последнее сообщение пользователя как текст запроса
   (`state["messages"][-1]`); пустой запрос возвращает «`{}`» без поиска.
2. Вызывает `search.query(query, sections=..., areas=...)`.
   - `sections` — служебная ось (типы разделов документа);
   - `areas` — предметные области, выбранные в интерфейсе; пустой список
     означает «по всей базе», а не «искать ничего»;
   - `limit` намеренно не передаётся из графа (`None`): провайдер берёт
     `RETRIEVAL_TOP_K` из настроек.
3. Пары `(Chunk, score)` превращаются в `Citation` через `to_citation()`
   (`search.py:46`) — именно эти словари уходят в интерфейс как «Источники (N)».
   `to_citation` ставит `clause=None` для табличных чанков (`contains_table`):
   у таблицы нет пункта, ссылка даётся на раздел.
4. Эмитит custom-событие `sources` (`graph.py:240`) — панель источников рисуется
   до первого токена ответа.
5. Собирает `followups` (`build_followups`, стр. 85) — детерминированно, без
   второго вызова модели:
   - по найденному пункту → «Подробнее по пункту X (DOC)»;
   - по документу без пункта → «Список положений из DOC»;
   - если остался слот → «Список всех найденных документов по охране труда»,
     а при пустой выдаче — «Что искать в базе знаний?».
   Дубли исключаются (`seen`), итог обрезается до 3 подсказок.
6. Полный набор попадает в `state["retrieved"]`; узел `assistant` вставляет
   полные тексты чанков в системное сообщение (см. п. 14).
7. Событие `followups` эмитится только если подсказки не пусты (`graph.py:242`).

## 3. Три исхода поиска (важно, qdrant_search.py:16)

Пустая выдача и сбой поиска — **разные вещи**, и их разделение принципиально:

| Состояние | Как возникает | Что делает ассистент |
| --- | --- | --- |
| Найдено | `query()` вернул список | Ответ опирается на выдержки |
| Ничего нет | `query()` вернул `[]` | «В базе знаний информации нет» (честный отказ) |
| Поиск недоступен | `SearchUnavailable` | «Поиск временно недоступен» |

Если при недоступном индексе вернуть пустой список, ассистент честно ответил бы
«информации нет» — авария замаскировалась бы под правильный отказ, и на защите
система выглядела бы как «всегда ничего не знающая». Поэтому в
`qdrant_search.py:16` выделен класс `SearchUnavailable` (наследник
`RuntimeError`), а граф при его перехвате помечает `retrieval_failed=True`
(`graph.py:200-203`) и даёт модели отдельный контекст (см. п. 14).

## 4. Протокол Search и форматы (search.py)

Протокол — один метод:

```python
async def query(query, sections=None, limit=None, areas=None) -> list[tuple[Chunk, float]]
```

`Chunk` — сырой фрагмент из индекса (`search.py:5`). `Citation` — итог под
номером `[n]` для интерфейса (`search.py:17`); `to_dict()` округляет `score`
до 4 знаков.

Критически важно разделение двух полей (`Chunk.text` и `Citation.snippet`):

- `snippet` — короткая выдержка (400 символов), идёт в панель «Источники»;
- `text` — полный текст чанка, уходит в контекст модели (`graph.py:145`).

Раньше в промпт попадал только snippet, и при медиане чанка около 822 символов
модель не видела больше половины пункта — включая числовые требования, которые
обычно стоят во второй половине абзаца. Поэтому два поля с разным назначением,
а не одно.

## 5. QdrantSearch: гибрид dense + BM25 + RRF (qdrant_search.py:77)

Один запрос `query_points` с двумя предвыборками (`prefetch`, стр. 102):

```
Prefetch(dense-вектор,   using="dense", filter, limit=prefetch_limit)
Prefetch(bm25-документ,  using="bm25",  filter, limit=prefetch_limit)
        │
        ▼
query = RrfQuery(Rrf(k=rrf_k))            ← слияние по рангам
        │
        ▼
limit фрагментов
        │  (если есть реранкер — сначала берут больше кандидатов)
        ▼
проверка порога близости (отдельный dense-запрос: _best_dense_score, стр. 170)
```

Четыре правила, нарушение которых не даёт ошибки, но портит выдачу:

1. **Фильтр ставится в каждый `Prefetch`** (стр. 108, 114), а не верхнеуровневый
   `query_filter`. Qdrant v1.19.0 проталкивает верхнеуровневый фильтр в ветки —
   обе формы дали одинаковый результат. Фильтр в `Prefetch` оставлен, чтобы
   ограничение было выражено там, где отбираются кандидаты, и не зависело от
   того, протолкнёт ли его конкретная версия сервера.
2. **`k` задаётся через `RrfQuery`**, а не через `FusionQuery` — у `FusionQuery`
   нет поля для параметров.
3. **Предвыборка не меньше `limit + offset`**, иначе при листании — пустые
   страницы. Код берёт `prefetch_limit = max(prefetch, fetch_limit)` (стр. 94).
4. **Порог по счёту RRF неприменим**: при `k=60` счёт не выше ~0,033, и любой
   разумный фиксированный порог отсечёт всё. Поэтому порог считается отдельным
   dense-запросом (см. п. 7).

Любые сбои оборачиваются в `SearchUnavailable`:
- `UnexpectedResponse` / `ResponseHandlingException` (Qdrant) — стр. 123;
- `OSError` / `TimeoutError` (сеть, таймаут) — стр. 126;
- любое другое исключение — стр. 129.

### Как собирается фильтр (_build_filter, стр. 45)

Из `areas` и `sections` строится `models.Filter` с двумя `FieldCondition` +
`MatchAny` по ключам `area` и `section_type`. Если обе оси пустые — фильтра нет
(`None`): поиск по всей базе.

### Запрос и реранкер

- Запрос кодируется эмбеддером с префиксом-инструкцией, если она задана
  (стр. 98-101); по умолчанию пустая (для bge-m3), нужна для qwen3-embedding.
- Если `reranker` передан — из индекса берётся `max(limit, reranker._candidates)`
  кандидатов, чтобы кросс-энкодеру был запас для выбора (стр. 88-92).
- Сбой переоценки: `RerankerUnavailable` логируется, реранкер выключается на
  весь процесс, выдача обрезается до `limit` — поиск без переоценки работает,
  просто ранжирует хуже. Если пакет не установлен, требуется `uv sync
  --extra rerank`.

### preflight (стр. 188)

Проверка готовности индекса на старте: алиас должен указывать на коллекцию и
та должна быть непустой (`count > 0`), иначе `SearchUnavailable`.

## 6. Индекс: поколения, уборка, лексический канал (store.py, bm25.py)

### Коллекция (store.py:78-109)

- именованный dense-вектор `dense` (косинус, HNSW `m=16`, `ef_construct=100`);
- разреженный вектор `bm25` с модификатором IDF (`SparseVectorParams`);
- payload-индексы `PAYLOAD_INDEXES` (стр. 18): `doc_id`, `doc_code`, `area`,
  `section_type` (KEYWORD) и `is_table_region` (BOOL) — **создаются до первой
  загрузки**, иначе HNSW строится без фильтровых рёбер и фильтрованный поиск
  деградирует;
- `chunk_payload` (стр. 32) собирает payload точки.

### Поколения (QdrantStore, стр. 59)

- `generation_name(version)` ⇒ `{alias}_v{version}` (стр. 75).
- **Алиас вместо поколения.** Размерность dense-вектора неизменяема, смена
  эмбеддера требует новой коллекции (`_v2`, `_v3`). `switch_generation`
  (стр. 190) атомарно удаляет старый алиас и указывает на новый; старые
  коллекции остаются как путь отката.
- **upsert пишет оба вектора** (`upsert_chunks`, стр. 113): запись только dense
  молча обнулила бы лексический канал. Каждый батч завершается только при
  `UpdateStatus.COMPLETED`.
- **«Записать, потом подмести»** (`sweep_document`, стр. 162): удаляет точки с
  чужим `sync_tag` (`must_not`), поэтому цикл `upsert → sweep` исключает
  временное отсутствие документа.

### Лексический канал BM25 (bm25.py)

BM25 считает **сам сервер Qdrant** (встроен начиная с 1.15.2): клиент
пропускает `models.Document` насквозь для модели `Qdrant/bm25` без обращения к
fastembed, поэтому образ ничего не скачивает, зависимость не нужна.
Проверочный минимум в коде — `MIN_SERVER_VERSION = (1, 16, 0)` (стр. 18),
`assert_server_supported` (стр. 38) проверяет версию на старте, чтобы 400 не
прилетело посреди демонстрации.

- `BM25_OPTIONS = {"language": "russian"}` (стр. 16) — **единственная точка
  правды** для записи И запроса. Документация Qdrant требует идентичности:
  расхождение ошибки не даёт, но ухудшает выдачу. `language="russian"`
  включает снежковый стеммер и русский стоп-лист.
- Без `language` сервер считает текст английским — русская морфология не
  схлопывается, «средству защиты» не находит «средства защиты», канал молча
  отдаёт ноль.
- `min_token_len` намеренно НЕ задаётся: выбросил бы аббревиатуры «ГО», «ЧС»,
  «СИЗ», на которых строится половина запросов по этому корпусу.

## 7. Порог релевантности (порог «честного отказа»)

Гибридный поиск **всегда** возвращает запрошенное число чанков — даже на вопрос
вне базы приедут настоящие пункты регламента. RRF-счёт для отсечения непригоден
(см. п. 5), поэтому после слияния делается отдельный dense-запрос
`_best_dense_score` (`qdrant_search.py:170`) с `limit=1`:

```
лучший косинус < retrieval_min_relevance (0.55)
        ⇒  выдача считается пустой  ⇒  честный отказ
```

Проверено на корпусе: релевантные запросы дают 0,68–0,72, посторонние
0,28–0,46, граница чёткая. Значение порога нужно перепроверять при смене
эмбеддера.

Порог отвечает на вопрос «есть ли в базе вообще что-то». Отсеивать им отдельные
чанки внутри одной выдачи нельзя: счета там почти плоские (медиана первой
позиции 0,666 против 0,613 на восьмой, диапазоны пересекаются). Точки отсечения
не существует — для фильтрации внутри выдачи нужен реранкер (см. п. 8).

Замечание о сбое probe: при неудаче `_best_dense_score` возвращает `0.0`
(стр. 183-185), а `0.0 < 0.55` — выдача станет пустой. Это текущее поведение
кода, порог в этой роли надёжен на живой точке.

## 8. Переоценка кросс-энкодером (rerank.py)

Гибридный поиск хорошо сортирует, но не отличает релевантного внутри выдачи.
Кросс-энкодер видит пару («запрос», «фрагмент») и разделяет начисто.

Замер на золотом наборе (41 вопрос, боевой корпус), переснят 09.08.2026 на
демо-машине (M5 Pro, 48 ГБ, `gpt-oss:20b`):

| режим | hit@1 | hit@3 | hit@5 | MRR | не найдено | поиск |
| --- | --- | --- | --- | --- | --- | --- |
| без переоценки | 0,561 | 0,707 | 0,780 | 0,648 | 9 из 41 | 127 мс |
| 10 кандидатов | 0,732 | 0,805 | 0,854 | 0,776 | 6 из 41 | 302 мс |
| 30 кандидатов | 0,756 | 0,829 | 0,878 | 0,805 | 5 из 41 | 604 мс |

Рабочая точка — 10 кандидатов (`rerank.py:105`): она забирает почти весь
выигрыш тридцати при вдвое меньшем времени. На демо-машине цена переоценки —
**+175 мс** к поиску (против +2,5 с на 16 ГБ, где кросс-энкодер конкурировал с
LLM за память) — то есть окупается и может быть включена. Половинная точность
(`half_precision=True`) даёт ускорение при неразличимом порядке выдачи.

> Таблица снята на демо-машине (MPS, 48 ГБ). В Docker-контейнере переоценка
> работает на **CPU**: 0,29–0,35 с на 10 кандидатов после загрузки модели.
> Первая загрузка весов из запечённого кэша занимает ~3–13 с и случается при
> первом вопросе после старта; дальше модель живёт в памяти и цена — стабильно
> ~+0,3 с к поиску на контейнерной сборке.

**В передаваемом образе веса запечены при сборке**: `deploy/Dockerfile`
ставит `.[rerank]` (sentence-transformers + torch), скачивает
`BAAI/bge-reranker-v2-m3` в `/opt/rerank-cache` и включает
`HF_HUB_OFFLINE=1`. Поэтому в образе достаточно одного тумблера —
`RERANK_ENABLED=1` — и больше ничего: с локально запечённой
моделью обращений наружу нет.

При запуске из исходников (не из образа) по-прежнему нужны три шага:

1. `uv sync --extra rerank` — поставить `sentence-transformers`;
2. заранее выкачать модель на машину демонстрации, чтобы `HF_HUB_OFFLINE=1`
   не ломал первый запрос;
3. `RERANK_ENABLED=1` и `RERANK_CANDIDATES=10`.

Если пакет отсутствует, поиск не сломается: `RerankerUnavailable`
перехватывается в `QdrantSearch`, переоценка отключается до перезапуска с
записью в лог, выдача остаётся в порядке гибридного поиска.

Цена автономности — размер образа: CPU-torch, sentence-transformers и веса
модели добавляют к образу порядка 4–5 ГБ (итоговый образ ~6 ГБ; сам кэш
`model.safetensors` ~2,3 ГБ). Смена `RERANK_MODEL` на модель, не запечённую
в образе, при `HF_HUB_OFFLINE=1` приведёт к `RerankerUnavailable` в логе —
это задумано: внешние API в офлайн-образе не вызываются никогда.

## 9. Число фрагментов в контексте

`RETRIEVAL_TOP_K=5`. Читать контекст модель обязана целиком, поэтому время
ответа растёт почти линейно с числом чанков (2 → 5,4 с; 5 → 16,6 с; 8 → 26 с
на слабой модели).

Но **резать число фрагментов нельзя вслепую** — перепроверено по золотому
набору (41 вопрос):

| `RETRIEVAL_TOP_K` | Переоценка | Не найдено | MRR |
| --- | --- | --- | --- |
| 5 | — | 9 из 41 | 0,647 |
| 5 | 10 канд. | 6 из 41 | 0,776 |
| 4 | — | 9 из 41 | 0,650 |
| 4 | 10 канд. | 6 из 41 | 0,776 |
| 3 | — | 12 из 41 | 0,630 |
| 3 | 10 канд. | 8 из 41 | 0,764 |

Снижение до 4 потерь не даёт (те же 9 недошедших без переоценки, 6 — с нею),
снижение до 3 теряет ответы, жившие на позициях 4–5 (12/8 недошедших).
Дефолт 5 безопасен; 4 допустимо (лучше всего вместе с переоценкой); 3 — нельзя
ни с реранкером. Старый замер на вопросе о сроке расследования это подтверждает:
нужный фрагмент стоял пятым, и при двух-трёх фрагментах модель выдавала
«в течение 10 дней» (числа, которого в корпусе нет вовсе), при пяти —
правильные «15 календарных дней». Обрезка не «чуть хуже», а превращает
правильный ответ в уверенную выдумку.

## 10. Грейдер релевантности (grading.py, выключен)

Отсеивает фрагменты моделью перед генерацией (`grade_chunks`, стр. 30). Оценка —
**одним вызовом на всю выдачу**, а не по фрагменту: батч даёт 72 % совпадения с
ручной разметкой против 62 % поштучно (поштучно модель не видит других
кандидатов и ставит всем «частично»).

Выключен по результату замера (qwen3:8b, Qdrant с боевым корпусом, 6 вопросов):

- честный отказ грейдер не покупает: оба внедоменных вопроса отсекаются порогом
  близости 0,55 ещё до грейдера;
- с отсевом «частично» он терял ответ в 2 случаях из 4 — искомое живёт именно в
  «частично» категории, поэтому `GRADING_KEEP_PARTIAL=1`;
- с `keep_partial=True` грейдер безвреден и бесполезен: пропускает всё насквозь,
  тратя время (стоимость вызова 10,8–23,3 с — больше, чем экономит).

Поштучный порог вместо грейдера не годится (см. п. 7): счета внутри выдачи
плоские, точки отсечения нет.

Оставлен как заготовка на другой корпус или более сильную модель. Три ловушки
структурированного вывода Ollama, разобранные проверкой:

1. Поле вердикта обязано быть перечислением (`Verdict = Literal["Р","Ч","Н"]`,
   `GradeResult`, стр. 16, 19-20): с обычной строкой модель наполняет его
   отсебятиной («помогает», «helpful»). `Literal` превращается в `enum` и
   включает ограниченное декодирование.
2. Длина массива вердиктов должна равняться числу фрагментов; зафиксировать её
   в схеме нельзя — грамматика **дописывает** недостающие. `grade_chunks`
   сверяет длины и при расхождении возвращает `None` (стр. 58-65).
3. Схема компактная: короткие коды вердиктов вместо объектов с номерами
   экономят время (генерация 11–16 ток/с против чтения 150–250 ток/с).

Сбой грейдинга (`None`) означает «оставить выдачу как есть»: ни ронять запрос,
ни втихую урезать источники из-за служебной модели нельзя.

## 11. Защита от выдумки (numbers.py, включена)

Критичная цифра: «Регистрация микротравмы — в течение 24 часов [1]», а срока
в корпусе нет вовсе. Ответ оформлен правильно, с маркером источника, и человек
примет его за требование регламента. Ни грейдер, ни усиление правил промпта не
помогли (доля верных отказов 6 из 10 на qwen3:8b в любом режиме). Поэтому —
детерминированная сверка чисел вне модели:

- из ответа вырезаются маркеры цитат `[1]` (`_CITATION`, стр. 10) — это не числа
  ответа;
- из текста извлекаются пары «число + следующее слово» (`_pairs`, стр. 15);
- каждая пара ищется в контексте (в отданных модели фрагментах);
- пара без подтверждения → приписка «Проверьте по первоисточнику»
  (`WARNING_TEMPLATE`, стр. 32).

Почему пара, а не голое число: цифры 5, 10, 15 стоят в номерах пунктов почти
каждого документа, так что «5 рабочих дней» найдётся просто потому, что есть
пункт 5.2. Пара «5 рабоч» таких совпадений не даёт.

Сравнение единицы на первые три буквы (`_UNIT_PREFIX=3`, стр. 12) закрывает
падежи: «24 часа» в ответе и «24 часов» в регламенте — одно и то же, а полное
совпадение развело бы их. Три буквы, а не пять: русские основы коротки, на пяти
«часа» уже не сходится с «часов». Три покрывают час/часа/часов, дня/дней,
год/года/годов. Риск лишнего совпадения мал — сравнивается пара с числом, а не
слово само по себе. Текст нормализуется: нижний регистр, `ё→е`.

Приписка — это предупреждение, а не отказ: число может прийти из соседнего, не
вошедшего в контекст пункта, а ответ остаться верным по существу. `annotate`
(стр. 38) вызывается из узла `assistant` (graph.py:178) только когда
`verify_numbers` включён и нет `retrieval_failed`.

## 12. Переписывание запроса (correction.py)

Урезанная форма Corrective RAG. Вызывается **только при пустой выдаче**
(`graph.py:205`) и ровно один круг. Промпт переводит вопрос с бытовой лексики на
язык регламента. Средняя цена по всем запросам близка к нулю — путь выполняется
только когда иначе был бы отказ.

- `MAX_REWRITE_CHARS=300` (стр. 9): результат длиннее — модель вернула
  рассуждение, а не запрос; в поиск такой текст отправлять нельзя.
- Результат чистится от кавычек и «лишних» символов, берётся первая строка.
- Неудача, пустой или неизменённый запрос → `None` («оставить всё как есть»):
  включается честный отказ, коррекция ничего не ломает.

## 13. Память и события (events.py, memory_gate.py, graph.py)

- `write_memory` (graph.py:266) извлекает устойчивые факты о пользователе
  (промпт `MEMORY_EXTRACT_PROMPT`) ТОЛЬКО когда `worth_extracting` (стр. 39):
  в последних двух репликах человека есть маркеры первого лица, глаголы
  представления/принадлежности или прямые просьбы запомнить (`_MARKERS`,
  memory_gate.py:5). Две реплики, а не одна: человек часто представляется
  отдельным сообщением, а следующим уже задаёт вопрос.
  Причины: извлечение — отдельный вызов модели (2,2–10,7 с), на безличном
  вопросе он уходит впустую, а на серии вопросов по регламентам память
  заполнялась журналом вопросов («пользователь спрашивал про...»), вытесняя
  настоящие факты (предел — 15 записей). Отбор «в сторону лишнего вызова»
  безобиден, ошибка в другую сторону дороже, поэтому список широкий.
- `conversation` для промпта = последние 4 сообщения × ≤500 символов.
- Синхронизация памяти (graph.py:313-322): чего нет в новом списке — `adelete`;
  чего не было — `aput` с новым uuid. Сбой `MODEL_ERRORS` или разбор JSON
  (`_parse_memory_json`, стр. 72) → память не трогают, запрос не роняют.
- События `sources` / `followups` / `trace` шлются через конверт
  `{"aist": {...}}` (`events.py`). Статусы `trace`: `model_unavailable`,
  `unavailable`, `rewriting`, `grading`.

## 14. Отказ модели и контекст узла assistant (graph.py)

- `_model_errors()` (стр. 31) собирает классы исключений клиентов модели:
  `httpx` (`TimeoutException`, `ConnectError`, `HTTPStatusError`),
  `ollama` (`ResponseError`), `OutputParserException`. Импорт мягкий — в тестах и
  сборке без Ollama пакетов может не быть. Если вызов `model.ainvoke` упал с
  одним из них, запрос не роняется: возвращается `AIMessage` с
  `MODEL_UNAVAILABLE_TEXT` (стр. 56) — «сервис генерации сейчас недоступен» — и
  эмитится `trace`.
- Контекст при `retrieval_failed` (стр. 135-141): модели даётся ровная фраза
  «поиск временно недоступен», запрещены общие знания и «информации нет».
- Контекст при обычной выдаче (стр. 143-149): полные тексты чанков с маркерами
  `[n]`, а не snippet; если выдача пуста — «В базе знаний нет выдержек для этого
  запроса».
- `today_msk` (стр. 64) — дата МСК (`%d.%m.%Y`). Тестам дату можно подать через
  `configurable.today`: без фиксированной даты ответы о сроках невоспроизводимы.
- `summary` (сжатая история) доклеивается отдельным системным сообщением с
  блоком `<internal_context>` (стр. 160-169) — «это служебное, не повторяй».
  Отказ сжатия (`condense_context`, стр. 247) лишь оставляет историю длинной.

## 15. MockSearch (mock_search.py)

Синтетический поиск для отладки интерфейса и тестов без индекса.

- Фиксированный корпус `_CORPUS` (стр. 38) из четырёх примеров документов.
- Поиск по совпадению слов: стоп-слова удаляются (`_STOPWORDS`, стр. 11),
  пунктуация заменяется пробелами, регистр нормализуется, одиночные буквы

## 16. Настройки (settings.py)

Читаются из окружения и `.env`, секретное поле `kb_password` не выводится.

| Переменная | По умолчанию | Роль |
| --- | --- | --- |
| `RETRIEVAL_PROVIDER` | `mock` | `qdrant` — боевой, `mock` — тест/отладка |
| `USE_MOCK_SEARCH` | 0 | устаревший флаг, при `True` перекрывает `RETRIEVAL_PROVIDER` |
| `QDRANT_COLLECTION` | `aist_chunks` | имя **алиаса** коллекции, не самой коллекции |
| `RETRIEVAL_TOP_K` | 5 | сколько фрагментов в контекст |
| `RETRIEVAL_PREFETCH` | 30 | кандидатов на канал до слияния |
| `RETRIEVAL_RRF_K` | 60 | константа слияния, подобрана замером на золоте |
| `RETRIEVAL_MIN_RELEVANCE` | 0.55 | порог честного отказа |
| `RERANK_ENABLED` | 0 (деплой: 1) | переоценка; в передаваемом образе включена, веса запечены, офлайн |
| `RERANK_CANDIDATES` | 10 | сколько верхних переоценивать |
| `GRADING_ENABLED` | 0 | грейдер (выключен по замеру) |
| `GRADING_KEEP_PARTIAL` | 1 | не резать «частично» категорию |
| `VERIFY_NUMBERS` | 1 | сверка чисел ответа с контекстом |
| `EMBEDDING_MODEL` | `bge-m3` | эмбеддер |
| `EMBEDDING_QUERY_INSTRUCTION` | `пусто` | префикс запроса (для qwen3-embedding) |

Про настройки как код (`settings.py`):

- `retrieval_provider` валидируется (`_check_provider`): опечатка в имени
  иначе молча откатила бы демо на синтетический корпус;
- `retrieval_top_k`, `retrieval_prefetch` и `ingest_batch_size` обязаны быть
  положительными (`_check_positive`);
- `qdrant_collection` — это алиас: поколения живут под `<alias>_v1`, `_v2`;
  переключение атомарно, приложение обращается только к алиасу;
- `resolved_retrieval_provider()` отдаёт фактическую реализацию с учётом
  устаревшего флага `use_mock_search`.

Вне рамок этого документа: чанкинг и деанонимизация корпуса, источники
(ApiSource/FilesSource), индексация и оркестрация — см. `docs/INGEST.md` и
`docs/DEPLOY.md`.
