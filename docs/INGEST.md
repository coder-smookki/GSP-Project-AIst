# INGEST — конвейер индексации базы знаний

Документация модуля `infrastructure/ingest/` и CLI `scripts/ingest.py`.
Описывает устройство офлайн-пайплайна, мотивировки решений и аргументы
командной строки. В коде комментариев нет — вся логика объясняется здесь.

## Общая схема

Пайплайн превращает корпус документов (HTML-статьи API и файлы `.docx`) в
набор эмбеддинговых точек в Qdrant.

```
источник -> разбор -> деанонимизация -> чанкинг -> эмбеддинги -> загрузка -> уборка
```

Ключевые свойства дизайна:

- **Функциональность.** Структуры данных неизменяемые (`frozen=True`); каждый
  шаг возвращает новый объект, поэтому повторный прогон на тех же входных
  данных даёт тот же индекс (`models.py:27`).
- **Ошибка документа не роняет прогон.** Ошибки собираются в отчёт, а код
  возврата CLI становится ненулевым. Молча пропустить документ нельзя —
  пользователь должен знать, что база неполна (`pipeline.py:136`).
- **Сначала записать, потом подмести.** Между шагами индекс содержит и старые,
  и новые точки, то есть поиск продолжает работать.

## Устройство прогона

Оркестрация — `ingest_documents`, `infrastructure/ingest/pipeline.py:78`:

1. `source.list_documents()` — список документов источника; при `limit`
   берётся срез (`pipeline.py:91`).
2. Каждый документ обрабатывается по одному в цикле (`pipeline.py:104`):
   загрузка сырья, разбор, чанкинг, определение областей, эмбеддинги,
   загрузка, уборка устаревших точек этого документа.
3. Ошибка одного документа не прерывает прогон — по ней формируется отчёт
   с текстом исключения (`pipeline.py:136`).

Формат выбирается в `parse_raw` (`pipeline.py:59`): `html` — через
`parse_article` из API-статьи, `docx` — через `parse_docx` по пути к файлу.
Неизвестный формат вызывает `ValueError`. Для `.docx` источник кладёт в
`content` путь к файлу: парсер читает архив сам, чтобы не держать его целиком
в памяти дважды.

### Режимы прогона

- **Обычный:** эмбеддинги считаются и точки записываются (`pipeline.py:131`).
- **`dry_run`:** разборка и чаннирование выполняются, но обращений к Qdrant
  и модели эмбеддингов нет — проверка конвейера на корпусе без поднятой
  инфраструктуры (`pipeline.py:128`).
- **Инкрементальный:** если документ не изменился по содержимому, самый
  дорогой шаг — вычисление эмбеддингов — пропускается (`pipeline.py:122-126`).
  Подробнее в разделе «Инкрементальная переиндексация».

## Отчёт о прогоне

`IngestReport` (`pipeline.py:36`) агрегирует результаты: список
`DocumentOutcome` по каждому документу и прежнюю коллекцию при переключении
алиаса. Полезные свойства:

- `total_chunks` — суммарное число загруженных чанков (`pipeline.py:43`);
- `failed` — документы, которые не удалось обработать (`pipeline.py:47`);
- `areas_histogram` — распределение документов по предметным областям
  (`pipeline.py:51`).

Форматирование человекочитаемого отчёта — `format_report`
(`pipeline.py:152`): итоговые счётчики, строка о переключении алиаса,
гистограмма областей, список «не отнесённых ни к одной области» документов
(в таких случаях печать обязательна: документ должен быть виден, а не
раствориться в общей куче) и список ошибок.

## Модели данных — `models.py`

Все структуры неизменяемые (`@dataclass(frozen=True, slots=True)`).

- `NAMESPACE` (`models.py:8`) — пространство имён для UUID-точек Qdrant.
  Менять нельзя: смена значения делает все существующие точки
  недостижимыми и требует полной пересборки индекса.
- `SectionType` (`models.py:11`) — тип раздела регламента. Определяет вес
  раздела при поиске: `SODERZHANIE` (оглавление) не индексируется вовсе,
  `NORMATIVNYE_SSYLKI` индексируется с понижением веса, остальные — на общих
  правах.
- `NOT_INDEXED` (`models.py:23`) — разделы, не попадающие в индекс:
  оглавление дублирует заголовки разделов и создаёт ложные попадания почти
  на любой запрос по названию раздела.
- `Atom` (`models.py:27`) — один пункт регламента вместе со своим
  маркированным списком: `clause` — номер пункта в исходной нумерации
  (например `4.1.4`), `text` — склеенный текст пункта, `is_table_region` —
  признак табличной зоны (в таблицах номер пункта недостоверен, поэтому
  цитата деградирует до уровня раздела), `order` — порядковый номер для
  склейки соседей.
- `ParsedSection` (`models.py:38`) — раздел с номером, заголовком, типом и
  атомами.
- `ParsedDocument` (`models.py:46`) — документ после разбора; содержит
  `doc_code` (код для цитат, например `Р-У2-59`), `sections`, а также
  заполняемый на шаге деанонимизации `glossary` и `content_hash`.
  Метод `atoms()` (`models.py:56`) возвращает сквозной список атомов всех
  разделов; `with_glossary()` (`models.py:59`) возвращает копию с подставленным
  словарём.
- `IngestChunk` (`models.py:64`) — единица индексации, точка Qdrant:
  `chunk_id` — стабильный идентификатор `<doc_code>#cNNNN` (на него ссылается
  золотой набор eval), `breadcrumb` — путь «Документ > Раздел > Пункт»,
  заменяющий overlap, `text`/`text_raw` — восстановленный и исходный текст,
  `aliases` — расшифровки для расширения запроса, `placeholders` —
   неразрешённые метки.

### Контентно-адресуемый идентификатор точки — `point_id`

`IngestChunk.point_id()` (`models.py:82`) строит ключ точки Qdrant. Qdrant
принимает идентификатором только целое число или UUID, поэтому `chunk_id` не
годится напрямую — но и выводить UUID из `chunk_id` нельзя:

- `chunk_id` = `<doc_code>#cNNNN`, то есть зависит и от позиции чанка в
  документе, и от `doc_code`, который для статей API выводится из порядкового
  номера в заголовке.
- Замерено на статье 88499 (227 чанков): вставка пяти абзацев в середину
  документа оставляет 118 чанков с прежним идентификатором при изменившемся
  тексте — загрузка молча перезаписывает их, счётчики сходятся, а цитата
  начинает указывать на другой пункт. Правка заголовка `(1)` на `(01)` меняет
  `doc_code` и осиротит все 227 точек разом.

Поэтому ключ **контентно-адресуемый**: выводится из места пункта в документе
и хеша его текста. Изменился текст — появилась новая точка, старая убирается
уборкой по `doc_id`; не изменился — точка обновляется на месте. Хеш берётся от
`text_raw`, то есть от текста **до** приклейки `breadcrumb`: breadcrumb
содержит `doc_code`, и через него нестабильность заголовка вернулась бы в ключ.

## Регулярные выражения — `patterns.py`

Единая точка правды для разбора регламентов. Все выражения якорные:
срабатывают только в начале абзаца или после явного разделителя. Это
осознанное ограничение — в тексте регламентов полно чисел, похожих на номера
пунктов (даты `12.02.1998`, номера законов `№ 28-ФЗ`, диапазоны `п. 3.2.8`),
и неякорный поиск даёт ложные разрезы атомов. Выражения проверяются тестом
на реальном корпусе: он падает, если появятся ложные срабатывания на
известных ловушках.

- `CLAUSE_HEAD` (`patterns.py:6`) — номер пункта в начале абзаца. Ведущая
  точка опциональна: конвертер источника срезает первую цифру у первого
  пункта раздела, превращая `1.1.` в `.1.` — такие номера достраиваются
  номером раздела (`restore_clause`).
- `CLAUSE_GLUED` (`patterns.py:10`) — номер, приклеенный к концу предыдущего
  предложения (тот же дефект конвертера, но в середине абзаца). Ищем только
  после `:` или `.`, иначе ловим дроби и даты.
- `SECTION_HEAD` (`patterns.py:14`) — заголовок раздела `4. Порядок проведения`.
  Ограничение длины намеренное: без него в заголовки попадают абзацы,
  начинающиеся с числа.
- `PLACEHOLDER` (`patterns.py:18`) — метка анонимизации `[ОРГАНИЗАЦИЯ_12]`.
- `GLOSSARY_LINE` (`patterns.py:20`) — строка словаря `[ОРГАНИЗАЦИЯ_18] — …`.
  Ровно этот дефект анонимайзера и есть канал восстановления: заменена
  аббревиатура, но расшифровка рядом уцелела. Разделителем бывает тире любого
  начертания или дефис.
- `GLOSSARY_LINE_REVERSED` (`patterns.py:24`) — обратный порядок строки словаря
  `Общество — [ОРГАНИЗАЦИЯ_1]`. Анонимайзер заменял и левую, и правую часть
  определения, поэтому канал восстановления двусторонний. Здесь метка стоит
  справа.
- `ABBREVIATION_LINE` (`patterns.py:29`) — словарь для уцелевших аббревиатур
  (`ЛВЖ — легковоспламеняющаяся…`); нужен, чтобы расширять запрос синонимами,
  а не только чинить плейсхолдеры.
- `DOC_CODE` (`patterns.py:33`) — код документа `Р-У2-59`, `P-U2-23`
  (латиница допускается: имена файлов транслитерированы).
- `API_TITLE_NO` (`patterns.py:37`) — порядковый номер в названии статьи API
  `(20) Регламент …`.
- `DATE_LIKE` (`patterns.py:41`) — дата в тексте, маркер ложного срабатывания
  номера пункта.
- `XML_JUNK` (`patterns.py:43`) — мусор XML, просачивающийся при некорректной
  выгрузке `.docx`.
- `TABLE_REF` (`patterns.py:45`) — ссылка на таблицу или приложение без
  содержимого, маркер табличной зоны.
- `_SECTION_TYPE_RULES` (`patterns.py:49`) — правила «заголовок раздела → его
  тип». Порядок важен, первое совпадение выигрывает. Для оглавления требуется
  **точное совпадение** всего заголовка, а не вхождение подстроки: правило
  `r"содержани"` ловило содержательные разделы вроде «Порядок содержания
  территории, здания и помещений» — по замеру корпуса выбрасывалось 6
  разделов, 61 атом, 19134 символа в 5 документах из 20, и на вопрос, ответ
  на который в базе **есть**, пользователь получал отказ. Настоящее
  оглавление при этом лежит в `<nav>` и отбрасывается раньше.

Служебные функции:

- `classify_section(title)` (`patterns.py:64`) — тип раздела по заголовку;
  `prochee`, если ни одно правило не сработало.
- `restore_clause(clause, truncated, section_no)` (`patterns.py:71`) —
  достраивает номер пункта, у которого конвертер срезал первую цифру: первый
  пункт раздела приходит как `.1.` вместо `1.1.`. Отдельно обрабатываются
  двузначные разделы: конвертер срезает **первую цифру**, у номера `12.1.`
  ведущая точка не появляется — получается `2.1.`, признак `truncated` равен
  `False`, и номер молча уходил бы в индекс неверным. Хуже того, пункт `2.1`
  в этих документах существует и означает другое (раздел 2 — термины), то
  есть цитата указывает на реальный чужой пункт. Достраиваем по сверке с
  номером раздела: если разрядная часть номера срезана, `section_no` с большим
  числом цифр оканчивается на первый компонент номера.
- `is_false_clause(text, match)` (`patterns.py:84`) — проверка, что найденный
  «номер пункта» не является частью даты.

## Разбор HTML — `html_parse.py`

Используется стандартная библиотека `html.parser`: у образа не должно быть ни
одной зависимости, способной сходить в сеть, а внешний парсер ничего не
добавляет — разметка редактора froala простая и предсказуемая.

Типичная разметка статьи (проверено на корпусе):

```html
<title>…</title><section class="cover">…<h1>…</h1></section>
<main><nav><ol>…оглавление…</ol></nav>
  <h2 id="section-1">1. Назначение и область применения</h2>
  <p>1.1. …</p><p>продолжение пункта…</p>
```

Два дефекта конвертера источника обрабатываются явно:

1. у первого пункта раздела срезана первая цифра — `.1.` вместо `1.1.`;
2. тело пункта разорвано на несколько `<p>`, а иногда наоборот — два пункта
   склеены в один абзац.

### Извлечение блоков

- `_BlockExtractor` (`html_parse.py:38`) — `HTMLParser`, превращающий HTML в
  плоский список `(тег, текст)`. Содержимое `<nav>` (оглавление) отбрасывается
  целиком (`_SKIP_CONTENT`), текст внутри таблиц помечается тегом `td`.
- `extract_blocks(html)` (`html_parse.py:93`) — защита от аномального ответа
  источника: при размере содержимого больше `MAX_CONTENT_CHARS`
  (4 МБ, `html_parse.py:33`) поднимается `ValueError`, чтобы один битый
  документ не съел память индексатора.
- `_GLUED_HEADING` (`html_parse.py:110`) + `recover_glued_headings` (`html_parse.py:115`):
  источник иногда не выделяет заголовок тегом, а приклеивает его к концу
  предыдущего абзаца, теряя первую цифру номера:
  `…более 0,45 м. 0. Требования к электроустановкам`. Признаки заголовка —
  стоит после конца предложения, начинается с номера, продолжается с
  заглавной буквы и не оканчивается точкой. Номер восстанавливается по
  ожидаемому следующему разделу: если найденный номер не совпадает с
  ожидаемым, но ожидаемый оканчивается на него (`10` против `0`), значит
  срезана первая цифра. Без сверки заголовок «0. Требования…» дал бы раздел
  с номером 0 и пункты вида `0.1`.
- `_split_clauses(text, section_no)` (`html_parse.py:157`) — разбивает абзац на
  пункты по якорным номерам; обрабатывает оба дефекта конвертера. Учитывает
  ложные совпадения (`is_false_clause`).

### Склейка и лимиты

- `_split_oversized(text)` (`html_parse.py:190`) — режет слишком длинный
  фрагмент по границам предложений. Лимит `MAX_ATOM_CHARS` = 1500
  (`html_parse.py:35`). В приложениях и бланках источник отдаёт целое
  приложение одним абзацем на десятки тысяч символов: такой атом бесполезен,
  потому что не влезает в контекст модели, а его эмбеддинг усредняет десяток
  разных тем. По достижении предела начинается новый атом с тем же номером
  пункта.
- `build_document(blocks, …)` (`html_parse.py:229`) — общая для всех парсеров
  сборка документа из плоского списка блоков: заголовки открывают разделы,
  абзацы режутся на пункты, продолжения приклеиваются. Подзаголовок `h3`
  раздел не закрывает, но обрывает склейку (следующий абзац не является
  продолжением пункта). Для табличных абзацев (`td`/`th` или наличие ссылки
  на таблицу) цитата деградирует до уровня раздела.
- `_doc_code` (`html_parse.py:214`) — код документа для цитат: из названия
  (если есть `Р-У2-59`), иначе порядковый номер из названия `(N) …` как
  `ДОК-N`, иначе суррогат `ДОК-<id>`. Код обязан быть стабильным — на него
  ссылаются цитаты в ответах и золотой набор eval.
- `_clean_title` (`html_parse.py:224`) — убирает служебный порядковый префикс
  `(N)` из названия.
- `parse_article(article, source="api")` (`html_parse.py:342`) — точка входа
  для API-статьи: проверяет наличие `id` и непустого `content`, вызывает
  `_doc_code`/`_clean_title`, прогоняет блоки через `recover_glued_headings`.

## Разбор .docx — `docx_parse.py`

Свой разбор вместо `python-docx` или `Docling` по трём причинам:

1. **Структурной разметки в файлах нет.** Проверено чтением
   `word/document.xml` всех трёх регламентов: ноль вхождений `w:pStyle`,
   `outlineLvl` и `numPr`. Главный козырь готовых библиотек — построение
   иерархии заголовков по стилям — здесь не даёт ничего, опираться всё равно
   приходится на регулярки по тексту.
2. **Вес.** Docling тянет в образ torch, который передаётся заказчику.
3. **Офлайн.** Чем меньше зависимостей, тем меньше поводов сходить в сеть.

`.docx` — это zip с XML. Нужны ровно две вещи: текст абзацев (`w:p` c
вложенными `w:t`) и границы таблиц (`w:tbl`), поэтому хватает `zipfile` и
выражений из `patterns.py`.

Ключевая тонкость: текст одного абзаца разложен по нескольким `w:t` — Word
режет его по границам форматирования. Склеивать надо **в пределах абзаца**,
иначе слова рвутся на куски прямо посреди предложения.

- `read_paragraphs(path)` (`docx_parse.py:34`) — открывает архив, читает
  `word/document.xml`, защищается от zip-бомбы (`MAX_XML_BYTES` = 64 МБ,
  `docx_parse.py:25`), заменяет `w:tab`/`w:br` на пробелы и возвращает пары
  `(текст абзаца, внутри ли таблицы)`. Позиции таблиц ищутся по `w:tbl`
  за один проход.
- `to_blocks(paragraphs)` (`docx_parse.py:70`) — превращает абзацы в блоки для
  общей сборки. Заголовки распознаются только по тексту: начинается с номера,
  короткий, не заканчивается точкой и без двойных пробелов —
  у пунктов регламента точка в конце есть почти всегда.
- `_extract_title(paragraphs)` (`docx_parse.py:96`) — название документа с
  титульного листа. Порядок попыток соответствует устройству титула:
  название в кавычках-ёлочках (уже в правильном регистре), затем подряд
  идущие строки капсом (там же название, но заглавными), затем первая
  содержательная строка. Кандидат должен содержать не менее 12 значимых
  символов после удаления плейсхолдеров — иначе «название» бесполезно и для
  показа, и для определения области знаний.
- `parse_docx(path, source="files")` (`docx_parse.py:130`) — точка входа:
  `doc_code` ищется в первых 40 абзацах и в имени файла, `updated_at` берётся
  из mtime файла.

## Деанонимизация — `deanon.py`

Корпус пришёл обезличенным: вместо аббревиатур и названий стоят метки вида
`[ОРГАНИЗАЦИЯ_12]`. Без восстановления поиск ломается — запрос «СОУТ» не
находит документ, в котором аббревиатура заменена меткой.

Ключевой факт, проверенный на корпусе из 20 статей раздела 44030: **один и
тот же идентификатор означает разное в разных документах**. Примеры
`[ОРГАНИЗАЦИЯ_18]`:

- статья 88499: «[ОРГАНИЗАЦИЯ_18] — пожарная безопасность»;
- статья 88535: «[ОРГАНИЗАЦИЯ_18] — сигнал оповещения»;
- статья 88532: «результаты анализа [ОРГАНИЗАЦИЯ_18] руководством».

Поэтому словарь строится **пофайлово** (`build_glossary`, `deanon.py:28`).
Глобальный словарь подставил бы уверенное враньё, а это хуже отказа:
пользователь не может отличить восстановленный термин от выдуманного.

Канал восстановления — непоследовательность самого анонимайзера: он заменил
аббревиатуру, но оставил рядом её расшифровку в разделе «Термины, определения
и сокращения». Читается только этот раздел (`SectionType.TERMINY`): поиск по
всему документу дал бы ложные пары из обычного текста с тире.

Правила:

- длина расшифровки от `MIN_VALUE_LEN` = 3 до `MAX_VALUE_LEN` = 120
  (`deanon.py:18..19`): короче — мусор разбора, длиннее — уже предложение,
  подстановка которого ломает читаемость;
- если в расшифровке тоже есть метка `[ОРГАНИЗАЦИЯ_…]` — подставлять нечего;
- `MASK` = «(наименование скрыто)» (`deanon.py:16`) заменяет невосстановимые
  метки. Показывать пользователю сырую метку нельзя — она выглядит как
   ошибка системы; угадывать значение нельзя тем более — правило прямое:
  честно сказать «нет данных» лучше, чем выдумать.

- `build_aliases` (`deanon.py:66`) — собирает уцелевшие аббревиатуры
  (`ЛВЖ`, `СМОЗиОБТ`) с их расшифровками: они не нужны для подстановки в
  текст, но полезны в индексе для расширения запроса — `легковоспламеняющаяся
  жидкость` находит чанк, где написано только `ЛВЖ`.
- `restore_text(text, glossary)` (`deanon.py:81`) — собственно подстановка:
  возвращает кортеж `(текст, список подставленных расшифровок, список
   неразрешённых меток)`. Нераспознанные метки всегда маскируются — плейсхолдер
   не должен попасть в ответ пользователю ни при каком исходе.
- `deanonymize(document)` (`deanon.py:99`) — шаг конвейера: строит
  объединённый словарь (расшифровки + аббревиатуры, приоритет расшифровкам)
  и прикрепляет его к документу через `with_glossary`. Подстановка в текст
  выполняется на шаге чанкинга, потому что чанку нужны обе версии — для
  индекса и для аудита.

## Чанкинг — `chunker.py`

Сборка чанков из атомов. Правила продиктованы форматом регламента, а не
общими соображениями:

- **атом = пункт** вместе со своим маркированным списком: разрывать пункт
  нельзя, иначе цитата «Р-У2-59, п. 4.3» перестаёт соответствовать тексту;
- **соседние короткие атомы склеиваются** до `TARGET_CHARS` = 900
   (`chunker.py:15`): одиночный пункт на 60 символов не несёт контекста и
  шумит в выдаче;
- **overlap отсутствует.** Вместо перекрытия текста используется `breadcrumb`
  — путь «Документ > Раздел > Пункт» в начале чанка (`_breadcrumb`,
  `chunker.py:20`). Overlap дублирует содержимое в индексе и завышает счёт
  документа, у которого совпадение попало в зону перекрытия;
- **оглавление не индексируется** (`NOT_INDEXED`).

Лимиты: `MAX_CHARS` = 1600 (`chunker.py:16`) — жёсткий предел размера чанка
(атомы длиннее уже разрезаны парсером); `MIN_CHARS` = 40 (`chunker.py:17`) —
короткие фрагменты отбрасываются, если их не удалось ни с чем склеить
(подписи, номера страниц).

`chunk_document` (`chunker.py:38`):

1. Группирует атомы: склейка допустима только внутри одного раздела и одной
   зоны (текстовой или табличной) — `_mergeable` (`chunker.py:30`). Пункты
   из разных разделов не склеиваются: цитата стала бы неоднозначной.
2. Для каждой группы считает `breadcrumb` и **восстанавливает плейсхолдеры
   по склеенному тексту вместе с breadcrumb** (`chunker.py:70`): заголовок
   раздела тоже содержит метки анонимизации, и без этого они утекали бы в
   индекс и в панель источников через путь чанка.
3. Предел размера считается по **итоговому индексируемому тексту**, а не по
   сырому: breadcrumb добавляет длину, а подстановка расшифровок делает
   текст длиннее (маска и расшифровка длиннее метки).
4. Формирует `IngestChunk` с уникальным и стабильным `chunk_id`, уникальными
   `aliases`/`placeholders` и признаком табличной зоны (в ней номер пункта
   недостоверен — цитата деградирует до уровня раздела).

`target_chars > max_chars` — конфигурационная ошибка, вызывающая `ValueError`:
такая комбинация молча породила бы чанки сверх предела.

## Предметные области — `areas.py`

Кейс требует, чтобы в интерфейсе можно было выбирать «области знаний»
(пожарная безопасность, охрана труда, ГО и ЧС). В источнике этой оси нет:
проверено на выгрузке — все 20 статей лежат в одном разделе
`section_id=44030`, поле `tags` у всех пустое. Поэтому область выводится
сама на этапе индексации.

Важно не путать две оси:

| Ось          | Что это                                                             |
| ------------ | ------------------------------------------------------------------- |
| `section_type` | структура **документа** (назначение, термины, процедура…) — служебная, нужна для весов |
| `area`        | **предметная** область — то, что выбирает пользователь               |

Подмена одной другой уже стоила бы дорого: фильтр по `section_type` со
значениями «процедуры и сокращения» отсекал 71 % корпуса.

- `classify_areas(doc_title)` (`areas.py:52`) — определяет области по
  названию документа. Правила не взаимоисключающие: «Регламент проверки
  знаний руководителей промышленной и пожарной безопасности» относится к
  двум областям.
- `UNCLASSIFIED` = `prochee` (`areas.py:9`): пустой список областей запрещён —
  документ с пустым `area` невидим при любом выборе пользователя, то есть
  тихо теряется. Он обязан быть виден хотя бы где-то («Прочее»).

## Инкрементальная переиндексация — `incremental.py`

Признак изменения — **хеш содержимого**, а не `updated_at` источника. Причина
в данных: у всех 20 статей выгрузки отметка времени попадает в один
сорокаминутный интервал 03.08.2026 — это след массовой заливки, а не
смысловых правок. Опираться на такую отметку значит либо переиндексировать
всё каждый раз, либо пропустить настоящее изменение.

Хеш считается по разобранному документу, а не по сырому HTML: разметка
источника меняется при каждом сохранении в редакторе, даже когда текст тот
же.

Состояние прошлого прогона читается из самого индекса — отдельного хранилища
нет. У каждой точки в payload лежит `content_hash` документа, поэтому
достаточно одного прохода `scroll` по коллекции (`load_index_state`,
`incremental.py:27`, страница — `SCROLL_BATCH` = 1024, `incremental.py:12`).

- `document_hash(document, pipeline_version)` (`incremental.py:15`) — SHA-256
  от (версии конвейера, `doc_code`, `doc_title` и всех атомов). Версия
  конвейера `PIPELINE_VERSION` (`pipeline.py:18`) входит в отпечаток: правка
  парсера, чанкера или правил деанонимизации меняет результат при том же
  исходном тексте, и без учёта версии инкремент пропустил бы документы,
  которые нужно перестроить. Поднимать при любом изменении, влияющем на
  состав чанков.
- `drop_documents(client, collection, doc_ids)` (`incremental.py:61`) — удаляет
  из индекса документы, исчезнувшие из источника. Вызывать **только при
  полученном без ошибок** списке документов: оборванный обход источника
  выглядит как «документы пропали», и уборка вычистила бы живой индекс.

## Версия конвейера — `PIPELINE_VERSION`

`pipeline.py:18`. Участвует в отпечатке документа, поэтому правка парсера,
чанкера или правил деанонимизации при том же исходном тексте заставляет
перестроить все документы даже при инкрементальном прогоне. Значение нужно
поднимать при любом изменении, влияющем на состав чанков. Формат — дата
плюс номер в тот же день (`2026.08.08-1`).

## CLI — `scripts/ingest.py`

Точка входа — `main` (`scripts/ingest.py:203`): разбор аргументов, настройка
логирования (`setup_logging`, `scripts/ingest.py:84`), запуск `asyncio.run`.
`KeyboardInterrupt` превращается в код `2`.

Коды возврата:

| Код | Значение |
|-----|----------|
| `0` | все документы обработаны |
| `1` | часть документов не обработана (подробности в отчёте) |
| `2` | прогон не начался: ошибка конфигурации или недоступный сервис |

`EXIT_OK`/`EXIT_PARTIAL`/`EXIT_FAILED` — `scripts/ingest.py:24..26`.

### Аргументы командной строки

Все описаны в `build_parser` (`scripts/ingest.py:32`):

| Флаг | Тип | По умолч. | Смысл |
|------|-----|-----------|-------|
| `--source` | выбор (`api`, `files`) | `api` | источник корпуса: API базы знаний или локальный каталог |
| `--corpus-dir` | строка | из настроек | каталог корпуса для `--source files` |
| `--section` | int | из настроек | идентификатор раздела базы знаний |
| `--limit` | int | все | обработать не более N документов |
| `--generation` | int | `1` | номер поколения коллекции: данные пойдут в `<alias>_v<N>` |
| `--switch-alias` | флаг | выкл | после успешного прогона переключить алиас на новое поколение |
| `--full` | флаг | выкл | полная переиндексация: не пропускать неизменившиеся документы |
| `--dry-run` | флаг | выкл | разобрать корпус и посчитать чанки, ничего не записывая |
| `--verbose` | флаг | выкл | подробный журнал |

### Ход прогона (`run`, `scripts/ingest.py:115`)

1. `build_source` (`scripts/ingest.py:94`) — источник: `FilesSource`, если
   `--source files`; иначе `ApiSource` с конфигом из настроек. Для API
   требуется `KB_EMAIL`/`KB_PASSWORD` в окружении или `.env`, иначе `ValueError`.
2. Подготовка индекса (только при обычном прогоне): настройка реестра
   моделей, эмбеддер, клиент Qdrant, экземпляр `QdrantStore`, создаётся
   коллекция-поколение `create_generation(collection, dim)`
   (`scripts/ingest.py:151..152`). При недоступности индекса — код `2`.
3. `sync_tag = run-<unix>` (`scripts/ingest.py:160`) размечает загрузку для
   уборки устаревших точек.
4. Инкремент: если не `--full`, состояние индекса читается через
   `load_index_state` (`scripts/ingest.py:162..166`).
5. `source.open()`, затем `ingest_documents` с переданными опциями
   (`scripts/ingest.py:172..`): колбек `show` печатает ход `N/total`.
6. `--switch-alias`: при успешном прогоне алиас переключается на новое
   поколение; при наличии ошибок алиас **не переключается** и печатается
   предупреждение.
7. В `finally` источник и клиент закрываются; выводится `format_report`.

Примеры:

```bash
# проверка конвейера без записи и без поднятого Qdrant
uv run python scripts/ingest.py --dry-run --source files

# полная индексация из API в новое поколение с переключением алиаса
uv run python scripts/ingest.py --source api --switch-alias

# первые три документа, без переключения алиаса
uv run python scripts/ingest.py --source api --limit 3
```

## Инварианты и заметки

- Идентификаторы точек и чанков стабильны между прогонами при неизменном
  входе: на `chunk_id` ссылается золотой набор eval.
- Плейсхолдер не должен попасть в ответ пользователю ни при каком исходе —
  нераспознанные метки всегда маскируются.
- Пустой результат классификации областей запрещён — «Прочее» вместо тихого
  исчезновения.
- Обрыв источника нельзя использовать для «уборки» индекса — `drop_documents`
  применяется только после успешного обхода.
