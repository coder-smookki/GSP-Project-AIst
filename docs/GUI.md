# GUI — веб-интерфейс ассистента

Документ описывает пакет `gui/`: Chainlit-приложение `chainlit_app.py`, слой
хранения и аутентификации `db.py` и вспомогательные функции `contract.py`.
В этот документ перенесена логика, которая раньше жила в комментариях кода;
исходник должен оставаться компактным, объяснения собраны здесь.

## Общая схема

```
браузер
   │
   ▼
Chainlit (gui/chainlit_app.py, порт 8000)
   │  авторизация: admin из env | gui_users (bcrypt)
   │  хранение истории: SQLAlchemyDataLayer → Postgres (схема Chainlit)
   │
   ├──► aegra (langgraph-sdk, AEGRA_URL=http://aegra:2026)
   │        └──► поток графа: plan → search_agent×N → finalize → assistant
   │            (sources, followups, trace, токены)
   │
   └──► /change-password (доп. роутер FastAPI поверх приложения Chainlit)
```

Интерфейс — тонкий клиент графа: вся генерация и поиск происходят в `aegra`,
а Chainlit отвечает за чат-макет, поток токенов, панель источников и
сохранение переписки между сессиями.

Пакет **не импортирует код агента**: контракт между ними — событийный поток
`client.runs.stream` и набор custom-событий в конверте `{"aist": {...}}`
(см. `agent/events.py` и `docs/RETRIEVE.md`).

## Архитектура

- `chainlit_app.py` — всё приложение: регистрация слоя данных, аутентификация,
  хэндлеры событий Chainlit, стриминг ответа и сопутствующий FastAPI-роутер
  для смены пароля.
- `db.py` — подключение к Postgres: схема Chainlit (история диалогов), таблица
  `gui_users` (пароли для входа), создание БД и миграции.
- `contract.py` — чистые функции без состояния: сборка входных данных для
  запуска графа, разбор конверта событий, форматирование источников, разбор
  события этапа, выбор финального текста ответа. Покрыты юнит-тестами
  (`tests/test_gui/`).
- `stages.py` — показ этапов работы графа шагами Chainlit (`cl.Step`).

## Поток работы

### Старт диалога (`on_chat_start`, chainlit_app.py:280)

1. `init_db()` вызывает и хук `on_app_startup` (chainlit_app.py:275): он
   создаёт схему до первого запроса, потому что Chainlit обращается к слою
   данных уже при аутентификации, раньше `on_chat_start`.; `seed_admin()` —
   заводит администратора из окружения.
2. Проверяется авторизация; без неё — сообщение «Требуется вход в систему».
3. Клиент `langgraph-sdk` к `AEGRA_URL`; ищется первый ассистент.
4. **Идентификатор треда aegra = идентификатор диалога Chainlit**
   (`thread_id = cl.context.session.thread_id`, chainlit_app.py:301):
   восстановление после перезагрузки не требует отдельных сопоставлений
   «диалог → тред» — соответствие по построению. `if_exists="do_nothing"`
   делает вызов идемпотентным: повторный вход в тот же чат не создаёт второй
   тред.
5. В сессию кладутся `client`, `assistant_id`, `thread_id`, `user_id`, `areas`.
6. Отправляется панель настроек (MultiSelect «Области знаний») и приветствие.

### Восстановление диалога (`on_chat_resume`, chainlit_app.py:362)

Chainlit сам рисует историю из слоя данных; хэндлер лишь поднимает клиент к
`aegra` и возвращает в сессию прежний `thread_id` (совпадает с идентификатором
диалога). Новых сообщений обработчик не создаёт — диалог отрисовывается.

### Смена областей (`on_settings_update`, chainlit_app.py:390)

`MultiSelect` приходит строкой или списком; нормализуется в список и кладётся
в сессию. Используется как фильтр `areas` при каждом запросе; **пустой список —
поиск по всей базе**, а не «ничего не искать».

### Сообщение (`on_message`, chainlit_app.py:420)

Поток `client.runs.stream` с `stream_mode=["messages", "updates", "custom"]`:

- **`messages/partial`** — токены AI-сообщений стримятся в пустое Message;
- **`custom`** — события `sources` (панель «Источники»), `followups`
  (подсказки следующих вопросов) и `trace` (этапы работы графа);
- **`updates`** — текст последнего завершённого AI-сообщения узла `assistant`.

**Ключ панели источников создаётся до цикла стрима** (`sidebar_key`,
chainlit_app.py:458): поток заканчивается только после узла `write_memory`
— это ещё один полный вызов модели, значительно позже события `sources`.
Если бы панель строилась после цикла, источники появлялись бы на несколько
секунд позже ответа.

Если источников не было вовсе — панель очищается, иначе она показывала бы
источники предыдущего вопроса.

Финальный текст выбирается `pick_final_text` (contract.py:203): ошибка →
последний завершённый AI-текст → самый длинный partial — fallback на обрывок
при разрыве потока.

### Этапы работы графа (`gui/stages.py`)

Планирование, ветки поиска и сборка занимают секунды, и раньше всё это время
интерфейс молчал: пустой пузырь ответа выглядел как зависание. Теперь каждый
узел графа шлёт событие `trace` в начале и в конце работы (`agent/graph.py`),
а `StageView` (`gui/stages.py`) рисует по ним шаги `cl.Step`.

| stage | Заголовок шага | Итог |
| --- | --- | --- |
| `condense` | Сжатие истории диалога | свёрнута / не менялась |
| `plan` | Планирование поиска | число подзапросов либо «поиск не требуется» |
| `search_agent` | Поиск в базе знаний: `<подзапрос>` | число найденных фрагментов |
| `finalize` | Отбор источников | число источников |
| `assistant` | Подготовка ответа | «Ответ готов» либо «Модель недоступна» |

Разбор события — `parse_stage` (`contract.py`), чистая функция без Chainlit;
отрисовка — `StageView`, тонкая обёртка над `cl.Step`. Существенное:

- **Ключ этапа у веток поиска включает подзапрос.** Ветки идут параллельно
  (`Send` в `agent/graph.py`), их события перемешаны в одном потоке, и без
  подзапроса в ключе вторая ветка закрывала бы шаг первой.
- **Шаги ведутся вручную (`send`/`update`), а не через `async with`.** Один
  блок `with` на этап не натянуть: события приходят вперемешку. Поэтому
  `start` и `end` проставляются явно — по ним интерфейс отличает идущий этап
  (мерцающий заголовок) от готового.
- **`StageView.close()` вызывается в `finally`.** Если поток оборвался, узел
  события о завершении не пришлёт, и шаг навсегда остался бы «выполняется»;
  вместо этого он закрывается с пометкой «Этап не завершён».
- **Сбой отрисовки гасится.** `handle` и `close` не выпускают исключений и
  только пишут в журнал: ответ пользователю важнее оформления этапов.
- **Пустое сообщение ответа отправляется не сразу**, а перед первым токеном
  (`ensure_message_sent`). Порядок в ленте задаётся моментом отправки: при
  ранней отправке шаги встали бы ПОД пузырём ответа, и ход работы читался бы
  после самого ответа.
- **Этап `condense` показывается только когда сворачивание дойдёт до модели**
  (`ContextManager.should_condense`): история почти всегда укладывается в
  бюджет, и иначе шаг мигал бы на каждом сообщении.

### Подсказки следующего вопроса (`on_followup`, chainlit_app.py:595)

Клик по подсказке **отправляет вопрос как обычное user-сообщение**, а не просто
пробрасывает текст в обработчик: иначе в переписке появляется ответ без
вопроса, и историю нельзя перечитать.

## Аутентификация

Схема входа — `@cl.password_auth_callback` (chainlit_app.py:191):

1. **Администратор из окружения.** Если `ADMIN_USERNAME`/`ADMIN_PASSWORD`
   заданы и совпадают — вход без записи в БД.
2. **Пользователь из `gui_users`.** Хеш пароля сверяется через `bcrypt`.
3. **Саморегистрация** (`ALLOW_SELF_REGISTRATION`, по умолчанию выключена,
   chainlit_app.py:147). Включать только для локальной отладки: при включённой
   любой незнакомый логин получал бы доступ к базе знаний, задав пароль
   первой попыткой входа.

Возврат из коллбэка `cl.User` обязательно предваряется `_ensure_persisted`
(chainlit_app.py:155): без записи пользователя в слое данных первый вход
показывал бы «Error fetching threads: Not Found: User not found» — интерфейс
запрашивает список диалогов раньше, чем слой данных успевает создать запись.
Вызов идемпотентен (см. `create_user` ниже).

### Смена пароля (`/change-password`, chainlit_app.py:632)

Дополнительный роутер FastAPI поверх приложения Chainlit. Требует текущий
пароль. Ограничивает попытки (`_MAX_ATTEMPTS = 5` за `_ATTEMPT_WINDOW = 300`
с): эндпоинт не несёт сессии, и без лимита он превращается в оракул для
подбора пароля и перечисления учётных записей. **Текст ошибки одинаков** для
«нет такого пользователя» и «неверный пароль»: разные ответы позволили бы
перечислять существующие учётные записи. Успех сбрасывает счётчик попыток.

## Слой хранения — `db.py`

### `GUI_DATABASE_URL` и создание БД

Подключение к Postgres из `GUI_DATABASE_URL`
(по умолчанию `postgresql://postgres:postgres@postgres:5432/chainlit`);
`_ensure_database` (db.py:130) создаёт БД, если её ещё нет.

Слой данных Chainlit работает через SQLAlchemy и требует схему подключения
`postgresql+asyncpg`; `async_database_url` (db.py:123) приводит строку к
асинхронному драйверу. Без этого слой падает на первой попытке запроса.

### Схема Chainlit (`CHAINLIT_SCHEMA`)

Взята **дословно из документации SQLAlchemyDataLayer**: слой обращается к
таблицам и колонкам по именам, поэтому отступление от схемы даёт ошибку в
рантайме, а не при старте. Если очередная версия Chainlit добавит колонку,
её надо дописать и в `CHAINLIT_SCHEMA`, и в `CHAINLIT_MIGRATIONS` — иначе
на существующих базах дефект вернётся.

Таблица `users` не конфликтует с нашей `gui_users`: первая нужна Chainlit
для привязки диалогов, вторая хранит пароли для входа. Файлов пользователь не
загружает, а панель источников — текстовый элемент, поэтому клиент объектного
хранилища не задаётся: он ложится в таблицу `elements` целиком.

### Миграции (`CHAINLIT_MIGRATIONS` → `_apply_migrations`)

База могла быть инициализирована старой версией Chainlit, а
`CREATE TABLE IF NOT EXISTS` существующую таблицу не меняет. Поэтому
колонки, появившиеся в новых версиях, добавляются отдельной миграцией:

```sql
ALTER TABLE "steps" ADD COLUMN IF NOT EXISTS "autoCollapse" BOOLEAN
```

Имя **квотируется**: иначе Postgres свёл бы `autoCollapse` к `autocollapse` —
и колонка никогда не была бы найдена. Именно это давал баг «пропадающих
сообщений после перезагрузки страницы» (Chainlit 2.11.1 вставляет
`autoCollapse`).

`_apply_migrations` (db.py:114) проглатывает `UndefinedTableError`: таблицы
появятся в `init_db` ниже, миграция применится в следующий проход.

### `gui_users`, `create_user`, `update_password`

- `create_user` (db.py:190) — bcrypt-hash и INSERT; на
  `UniqueViolationError` возвращает `False` (это делает функцию идемпотентной
  для `_ensure_persisted`).
- `update_password` (db.py:219) — сверка текущего пароля, длина нового ≥ 4,
  обновление хеша.
- `seed_admin` (db.py:244) — заводит администратора (`ADMIN_USERNAME`/
  `ADMIN_PASSWORD`, роль `admin`).

## Функции-контракт — `contract.py`

- `build_input` (contract.py:159) — полезная нагрузка запуска графа: сообщение
  пользователя + опциональные `sections`/`areas` и флаг
  `always_answer_with_db` (принудительный поиск в базе, обходя роутер
  планировщика). `sections` — служебная ось,
  из интерфейса не задаётся (оставлена для отладки и тестов); пустые списки
  не попадают в запрос.
- `decode_aist_envelope` (contract.py:176) — достаёт конверт `{"aist": {...}}`
  из события: из верхнего уровня или из `chunk["params"]["data"]` (новый
  формат Chainlit).
- `format_sources` (contract.py:184) — рендер панели «Источники»: номер `[n]`,
  код документа, «· п. <clause>», заголовок и фрагмент. Если пункта нет —
  ссылка без пункта (табличная зона).
- `parse_stage` — разбор события `trace` в `StageEvent`: ключ этапа, заголовок
  шага, признаки «выполняется»/«сбой» и короткий итог. Незнакомый этап даёт
  `None`: интерфейс молча пропускает такое событие, а не выдумывает заголовок.
- `pick_final_text` (contract.py:203) — порядок выбора текста ответа (см. выше).

## Области знаний (`AREA_CHOICES`, `DEFAULT_AREAS`)

`AREA_CHOICES` — предметная ось, которую выбирает пользователь. Раньше здесь
были типы разделов документа (`sokrashcheniya`) — **другая, служебная ось**:
она не отвечала требованию кейса «выбор областей знаний». Хуже: выбор по
умолчанию отсекал 71 % корпуса, а значение `sokrashcheniya` не существует
вовсе — оно не находило ничего.

`DEFAULT_AREAS = []` — пустой список означает поиск по всей базе, а не по
пустому множеству. Непустой список по умолчанию молча сузил бы поиск, и
пользователь не понял бы, почему ответа нет.

## Запуск

- Локально: `uv run chainlit run gui/chainlit_app.py --host 0.0.0.0 --port 8000`
- В docker-compose (см. `deploy/docker-compose.yml`, сервис `gui`):
  `AEGRA_URL`, `GUI_DATABASE_URL`, `ADMIN_USERNAME`/`ADMIN_PASSWORD`,
  порт `8000`. Образ с зависимостями железно собирается и поднимается
  `chainlit run` (см. `deploy/Dockerfile.gui`).
